# 需求说明

确认日期：2026-11-02（Asia/Shanghai）。本文根据本轮对话中已确认的需求整理。

相关设计草案：[Agent 交互与任务说明](design/agent-interaction.md)。

## 使用方式

用户在 Codex 或其他外部指挥 agent 中下达指令，连接本系统，指挥 ZCode 完成工作。支持输入总目标，也支持输入已经拆分好的任务。

安装、账号准备和连接配置一次完成，日常用一句指令开始工作，无需操作 VS Code。首期指挥与 ZCode 位于同一执行环境，也可以同处远程环境，由 VS Code 远程查看。指挥在 CLI、tmux 等终端环境运行时也能工作。

## 指挥与 ZCode 的分工

外部指挥负责安排、跟进、组织验收和返工，ZCode 负责具体实施。

用户只给目标、未提供验收条件时，由指挥整理少量可观察的完成标准。影响最终效果的关键歧义先问用户，其余自行补全，不要求用户逐项手动审批。

验收由指挥根据任务自主选择合适的方式和执行者，也可以安排原账号的 ZCode 继续验收，不需要每次询问用户。使用 ZCode 实例验收时占用对应账号；使用 ZCode 之外的独立验收资源时不占用 ZCode 账号，原实施账号可以执行其他独立任务。

验收绑定固定的交付版本，不因原账号后续工作改变待验收成果。成果最终整合进项目后，再检查实际交付成果。

多个账号共用一份项目，还是分别修改，由指挥根据任务决定。默认完成要求是成果整合进项目，并通过验收。

## 共享账号池

多个 Codex 会话或其他指挥 agent 可以同时共享账号池，由系统统一分配账号，通常由不同指挥分别处理不同项目。一个 ZCode 实例对应一个账号，例如 3 个实例对应 3 个账号；一个账号同一时刻只能由一个指挥控制。

ZCode 实例内部不启动或派发子 agent，以避免同一账号内并发引发繁忙。外部指挥将每个实例视为不派生子 agent 的独立 ZCode 执行者，合理拆分任务，把需要并行的工作分配给不同账号的实例。

ZCode 执行结束并保存成果与上下文后，即可释放账号，不必等到整个用户总任务或外部验收结束。原指挥后续继续或返工时重新申请账号，不保证仍使用原账号。

## 并发设置与资源分配

全池总上限、各指挥的默认配额和本次任务配额分层控制。面板中的人工默认设置持续有效。

用户在提示词中明确“这次使用 N 个账号”时，临时覆盖本次任务的默认配额，任务结束后恢复采用默认值。例如，面板默认 2 个账号，本次任务可以临时使用 3 个账号。改变全池上限需要用户明确说明。

降低并发不打断已有任务；设为 0 时停止相应范围的新派发，已有任务继续。

可用账号不足、多个指挥等待时，公平轮流分配账号，不打断正在运行的任务。申请 N 个账号但实际可用数量不足时，先告知实际资源，等待用户确认后，才能用可用账号部分推进。

## 额度与故障处理

默认低额度切号阈值为剩余 5%，可以配置。当前账号低于阈值，但任务仍正常执行时，不打断当前任务；当前任务完成后，后续派发换号。当前任务因额度受阻时，交接后续工作。

所有账号都低于阈值时，暂停新派发，通知用户决定后续安排。

有可用额度时，繁忙、限流、超时等通道故障持续重试。基础重试间隔默认 5 秒，可在面板调整；服务有明确等待要求时优先遵守。只有确认原命令没有实际执行且适合重试时，才再次发送，不因通信超时盲目重发。代码错误和验收失败由指挥判断如何返工。

某个子任务在已确认没有实际执行的故障恢复等待中，账号先保留给原任务重试。连续等待默认 2 分钟，可在面板调整；达到后可以归还共享池，原任务保留，按公平规则重新排队，重新获得账号后继续重试。仍在执行或执行状态未知时，即使等待时间已到，也不能归还账号，应先核实。原命令虽尚未开始、但仍可能排队启动时，也不能归还；归还前须确认原执行已经失败、终止或停止。

连续等待只按当前等待段计时；有可信证据确认恢复实际执行时，本段等待结束，后续再次进入故障恢复等待时重新计时。请求发送成功、收到回执或健康检查成功，都不等于恢复实际执行。重试次数仅用于累计展示和错误统计，不设总重试次数上限，也不作为归还账号的条件；恢复执行不清空历史错误次数。

执行静默核查默认在连续 15 分钟缺少新的可见执行活动时触发，可在面板调整。新输出、工具或命令步骤的状态变化、新的检查结果等属于可见执行活动；错误、重试和健康检查不算，文件变化仅作辅助。这些活动不等于目标已经取得实质进展，缺少可见活动也不自动判为卡死或失败。

静默时由程序只读核查原任务，不发送“你还在吗”等提示词，不重新派发或要求重做。原任务仍在活动时，显示执行中但静默；状态不明时，显示待核实并保留账号占用；明确故障时，按既有规则恢复。

## 指挥中断与接手

指挥中断后，已派发的工作和通道重试继续；需要后续新安排、验收等决策时，等待指挥恢复。仍在执行的账号不因指挥断线而立即释放。

用户明确要求时，另一会话可以接手用户总任务，并转移控制权。旧指挥恢复后，应知道任务归属已经改变，避免双重指挥。

新指挥读取精简续接记录，先简报已完成内容、未决事项和下一步。常规工作直接继续，必要决策再问用户。

## 面板与汇报

VS Code 用于可视化查看和交互。界面支持共享账号池和当前项目两种视角，概况中任务与账号信息并列突出，详细内容按需展开。

### 任务流程与验收

任务进度展示总目标、拆分计划、当前阶段、子任务清单及状态。总任务界面同页展示任务信息、整个任务的流程图和账号分配，另设账号额度界面。

流程图按实际任务关系绘制，阶段数量随任务变化，展示串行、并行分支、汇合与依赖关系。以阶段为节点，显示阶段名称、状态及参与账号；展开节点可查看子任务和每项任务分配的账号。

流程图区分未开始、进行中、受阻或待处理、已完成，使用不同视觉标记并配状态文字，已完成阶段突出点亮。阶段达到自身目标，并由指挥根据阶段完成标准及必要验收结果确认完成后点亮，无需用户逐阶段手动操作。

已点亮的阶段后来需要返工时，取消已完成显示，恢复为返工或重新进行状态；满足完成条件后再次点亮。

实施状态与验收状态分别显示，并展示验收执行者；使用 ZCode 之外的独立验收资源时，允许原实施账号已空闲，而任务仍处于验收中。

### 账号与额度

账号池列表默认显示账号标识、状态、剩余额度、当前指挥和任务，以及分类错误次数。更多内容进入账号详情查看。

存在多个官方额度窗口时，默认展示摘要，突出影响当前使用的额度。展开后可查看各窗口剩余比例、官方能提供的具体用量和恢复时间；这些内容以官方实际返回的信息为准，不编造缺失数据。

自动刷新与手动刷新同时提供，展示更新时间，并提示查询失败和数据过旧，避免旧值被当作最新数据。

### 错误记录

分类错误可以按账号和任务两层查看，并可选择时间范围或当前任务。记录实际发生的错误次数：同一任务连续繁忙 5 次后成功，应显示繁忙 5 次，并标记已恢复。

### 日志、交付与验收结果

日志默认展示派发、开始、错误、重试、交接、验收等关键事件，详细日志按需展开。

交付与验收结果默认展示摘要，包括完成内容、修改文件、检查结果和验收结论，可展开查看差异及相关产物。

### 资源操作与待处理事项

概况直接提供常用资源和配额操作，包括全池上限、各指挥配额、账号启停和暂停新派发等；更具体的账号与任务操作进入对应详情。

概况集中汇总账号不足待确认、全部账号低额度等需要处理的事项，并在对应项目、任务和账号处关联标记，可以点击查看原因并处理。

### 通知与汇报

在关键阶段和需要用户决策时汇报。VS Code 打开时，需要用户决定的事项发送 VS Code 通知，同时保留在面板待办中。能够自动恢复的普通错误只记录在面板中，不逐次弹出通知。

用户不在线时，需要决定的事项通过当前指挥入口说明原因并保留待办，只阻塞依赖该决定的步骤；其他已授权且不依赖该决定的独立工作继续。用户回来或指挥重连时，汇总未决事项。继续独立工作仍须遵守资源不足的确认要求，以及全部账号低于阈值时暂停新派发的要求。

## 工程与使用约束

用户不是专业程序员。具体程序形态由实现方按实用性自主判断，以开箱即用、配置最少、维护成本最低为标准，不要求用户做技术选型。现有架构和交互流程都可以重新评估和简化，不因已有实现而默认沿用。

合理切分代码与文档，控制 agent 与程序交互的复杂度、次数、内容量和 token 消耗，减少重复说明、重复传递上下文和不必要的交互步骤，以简单高效为目标。多账号环境配置、Git Worktree 建立与清理、端口和子进程管理等繁重的机械逻辑，全部封装为代码，不让 agent 每次依赖长篇自然语言上下文逐步操作。

状态修改、阶段变化与界面展示更新应一并设计，明确程序负责的部分和需要 agent 参与的部分，以节省 token、提高效率和简化维护为标准。避免为了可视化增加繁琐的状态维护和过多交互，不以 agent 逐项操作界面作为默认方式，使 agent 主要处理必要的任务安排和语义决策。界面展示的更新不替代指挥对阶段完成的确认。

确有需要 agent 自动感知的调度指南或工具说明时，采用极简说明，在使用程序时按需自动加载，避免无关上下文常驻。说明形式和文档是否拆分按实际效果判断，有收益才拆分，不强制采用 Skill 或常驻 Prompt。

遵循 KISS/YAGNI，保持简单并聚焦核心闭环。不引入不必要的复杂抽象、兜底补丁或测试，不搭建臃肿的测试脚手架。必要的验证和错误处理仍需保留，不因追求极简而削弱持续重试、账号互斥等已确认需求。
