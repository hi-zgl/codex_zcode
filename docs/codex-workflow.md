# 指挥使用约定

[需求说明](requirements.md) · [交互责任](design/agent-interaction.md) · [上下文预算](context-policy.md)

初次按[工作台指南](ui/implementation.md)配置同一执行侧的 MCP。日常只有五个工具入口：`zcode_submit_work`、`zcode_wait_work`、`zcode_advance_work`、`zcode_inspect`、`zcode_pool_control`。简短指南随 MCP 自动提供，工具 schema 给出当次参数，无需预装 Skill 或常驻长提示词。

1. 用户只给目标时，先补充少量可观察的完成标准；只询问影响效果的关键歧义。交办目标、阶段依赖和已授权首批工作，注明本次明确申请的账号数。
2. 使用总任务 ID 与 revision 等待关键变化；普通重试由程序负责。无变化时只保留游标，不读取完整日志或重复整个池。单次等待需符合指挥宿主工具的时长能力。
3. 收到交付后，按固定 delivery 安排适当验收。外部验收开始、执行者与结论要登记；ZCode 验收占账号，独立外部验收不占账号。
4. 依据阶段目标、完成标准与必要验收确认阶段，或安排返工；可在一次推进中同时登记结论、整合和下一批。执行成功不等于阶段或总任务完成。
5. 成果整合进项目后，针对实际整合版本检查，再确认总任务完成。需要详情才用 inspect 读取结果、日志或差异。

资源不足必须先告知实际可用数并取得用户确认，才能用少于申请数的账号推进；全部账号低于阈值时暂停新派发。全池上限只在用户明确要求时改变，本次配额不永久覆盖人工默认设置。

控制台无需逐步手动操作。项目、阶段、账号和待办由事实投影，指挥不填颜色或第二套状态。指挥中断后，已派发任务与安全恢复继续；新的语义安排等待恢复。用户明确要求接手时转移控制版本，旧指挥不得继续控制。

需要用户决定时说明原因并保留待办，其他已授权独立工作继续；用户回来或指挥重连时汇总未决事项。项目实现过程的未决事项维护在[当前清单](open-items.md)，解决后并入对应设计。

需要启动或收工时明确使用 `pool_control` 的 `start` / `shutdown`；`read` 不启动后台。查询失败不能当作任务已停止，不重复提交结果未知的请求。
