# 模型繁忙时立即在原会话继续

[开发与运行](development.md) · [中断与重新附着](recovery.md) · [MCP 上下文预算](context-policy.md)

daemon 仅在确认当前原生回合因明确的模型繁忙错误失败、该回合已终止且会话没有活动执行后，立即在原会话发送固定文本 **“继续”**。不增加退避计时或人为等待，不重新发送原任务提示词，不创建新任务，也不轮换账号、模型或 Worker。检查和原生请求本身仍需要实际运行时间。

## 次数和配置

`dispatch_task` 的 `busy_retry_limit` 默认是 **3**，表示原任务初次派发之后最多再发送三次“继续”。可设为 `0` 关闭自动续跑；参数接受 `0–10`，建议保持默认的三次上限。次数在发送续跑命令前持久化；即使 daemon 重启也不会重置。

```json
{
  "workspace_id": "workspace-1",
  "worker_id": "worker-1",
  "request_id": "stable-task-request",
  "prompt": "完成当前任务并验证结果",
  "busy_retry_limit": 3
}
```

每次续跑使用新的原生命令 ID，客户端的原任务 `request_id` 保持幂等含义。不会将原始提示词再次放进续跑请求。上限耗尽后结束该任务并报告繁忙阻塞；不会继续循环。正常成功后的本地核验与结果生成仍只运行一次。

## 哪些错误可以继续

只有明确的模型或服务暂时繁忙、过载、达到容量的错误归为 `model_busy`。例如错误中的 `provider_overloaded`、`The model is busy` 或“模型繁忙”；这些词必须来自原生错误字段，且能证明属于当前回合。

- 风控 `risk_blocked` 和鉴权 `auth_invalid` 优先于繁忙提示，按原有规则阻塞任务与账号。
- 额度不足、配额耗尽、明确 `Retry-After` 等要求等待的信息归为 `rate_limited`，不会立即继续。普通 HTTP 429、并发限制也不触发；429 只有同时存在明确繁忙证据且没有上述冲突时才可能归为 `model_busy`。
- 普通 503、502、超时或断线属于 `server_error`，不能仅凭状态码当作繁忙。未知错误、未知执行状态、身份冲突、未终止回合或仍有活动执行时不发送“继续”。
- 工具调用的失败、工具输出及 assistant 普通正文中的 busy/“繁忙”不是续跑证据。停止请求一旦被记录，也阻止任何后续自动续跑。

即使错误分类正确，续跑仍要求新的原生快照证明：当前命令精确匹配唯一失败回合、`activeWorks` 为空、账号可用、会话/工作区一致、provider/model 与原任务绑定一致，且没有进入过本地核验。检查不通过时保留可供检查的状态，不猜测原命令是否仍在执行。

## 原生错误归属

会话级 `control.lastError` 可能保留上一回合的错误。适配器不把它直接归给最后一条 turnHeader，更不会附给所有历史失败回合。错误有 `sourceCommandId` 或产品 `turnId` 时，各身份字段必须一致且唯一；存在冲突即拒绝归属。

对于本机已检查的官方 **3.16.3**，`zcode.cjs` 的 `onTurnError(event)` 在同一批投影操作中生成失败 turnHeader 和 `control.lastError`：两者的 `endedAt` / `at` 都取自 `this.ms(event)`，而该方法返回 `event.timestamp.getTime()`。因此适配器允许无显式命令 ID 的错误通过 **`lastError.at === 唯一失败回合的 endedAt`** 归属，同时要求时间为有效正数且 `startedAt <= endedAt`。时间碰撞、缺失、无效数值或只落在大致时间区间都不足以证明归属；这不是对任意版本时间语义的猜测。

逻辑 frame 内的所有 delta 应用完毕后才发布语义事件，兼容批内“失败 header 在前、错误状态在后”的顺序。错误先于失败 header 跨 frame 到达时，可在终止事件中使用已保存的精确时间证据。若终止时仍没有可归属证据，则按未知失败处理，不人为等待或补发请求。

已录制的 `official-preparation-error.json` 包含 `code`、`message`、`recoverable`、`at`、`source`、`detail`、`underlyingErrorMessage` 和 `attribution`；其中 `at: 0` 是脱敏值，不能作为时间归属正证据。该 fixture 是准备阶段错误，也不是实际繁忙响应。繁忙文字、状态码冲突和有效时间的组合由本地协议测试构造，未调用真实模型。

## 重启和精简输出

任务和每次原生命令分别持久化发送意图、ACK、终止证明及繁忙证据。daemon 在重启后重新核对原命令和原会话；已提交但接收状态不明的续跑意图不能再次发送。执行状态不明时仍按 [重新附着规则](recovery.md) 处理，不能通过重发原任务来恢复。`reconcile_task` 保持只读对账含义。

状态库从 schema v1 升到 v2 时，旧任务缺少的 `runtimeBinding` 保持为空，初始续跑次数为零，繁忙资格也不凭空补齐。此类任务仍可按原命令保守重新附着、取消或完成核验，但不会自动发送“继续”，也不会猜测账号或 provider/model 绑定。

`overview`、`wait`、`get_result` 和恢复响应中的续跑状态只公开：

```json
{"retry":{"used":1,"max":3,"reason":"model_busy"}}
```

`used` 是已经提交的续跑次数，`max` 是任务上限，`reason` 是固定值。日志中的续跑事件沿用同一白名单。MCP 不回传续跑所用的上下文、原任务、原生错误文本或原生命令明细；繁忙错误诊断使用固定文案。最终 JSON 文本的 **16 KiB** 上限不变。

本地测试覆盖中英文繁忙分类、风险/鉴权/配额优先级、普通 429/503、工具与正文排除、跨回合残留错误、时间碰撞、整批事件归属、精简输出及预算。真实服务返回的未识别形态会保守停下，不能将这些测试视为所有云端繁忙状态的实测保证。
