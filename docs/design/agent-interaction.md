# 指挥交互与状态责任

[需求说明](../requirements.md) · [设计入口](README.md) · [当前验证](../validation/current.md)

外部指挥负责安排、跟进、验收和返工，ZCode 实例负责具体执行。程序封装账号选择、环境与目录准备、执行去重、状态记录、保存交付和安全恢复。一个事实只记录一次，界面从事实生成，不要求指挥再设置颜色或维护平行状态。

## 日常入口

| 动作 | MCP 工具 | 指挥提供 | 程序负责 |
| --- | --- | --- | --- |
| 交办 | `zcode_submit_work` | 目标、项目、少量完成标准、阶段依赖、明确授权的工作与本次配额 | 登记总任务、公平申请资源、准备目录并执行 |
| 等待 | `zcode_wait_work` | work ID、指挥身份和上次 revision | 等待关键变化，返回短摘要或无变化游标 |
| 判断并推进 | `zcode_advance_work` | 验收安排/结论、阶段确认/返工、整合、下一批或总任务完成 | 一次记录判断并执行授权动作，更新展示 |
| 按需查看 | `zcode_inspect` | work、结果、日志或差异的引用与游标 | 返回有界事实，不重放会话全文 |
| 池控制 | `zcode_pool_control` | 开工启动、完成后自动收工或明确的资源设置 | 统一应用策略与安全收工检查；查询不启动后台 |

开工与收尾采用[指挥使用约定](../codex-workflow.md)，简短规则由 MCP 自动提供，不要求用户记住提示词或逐次提醒收工。

`wait_work` 的单次时长受宿主工具能力限制；当前参数默认 45 秒，可在宿主支持时延长至 300 秒。无变化只返回游标，普通错误与重试不唤醒指挥。宿主支持通知或等待时优先使用；不宣称 MCP 能保证无限等待或主动推送。

新增阶段和依赖用于表达组织关系，不授权程序自己决定全部后续工作。用户只给目标时，指挥补充少量可观察的完成标准；影响最终效果的关键歧义才询问用户。

## 实施、验收与阶段

程序从运行事实记录开始、结束、占用、额度、错误与成果。指挥登记外部验收的开始、执行者、固定交付和结论，并根据阶段目标及必要验收确认完成。执行成功与命令通过不能自动替代验收或阶段确认。

外部独立验收不占用 ZCode 账号；用 ZCode 验收占对应账号。返工撤销阶段完成显示，后续满足条件再确认。最终整合后，应检查实际交付版本。可在一次推进中合并验收结论、阶段确认和下一批安排，减少重复交互。

## 按需说明与续接

MCP 的简短使用说明随程序自动提供，具体参数由工具 schema 给出。只有派发、验收和交接时才补充对应目标、约束、证据和成果引用；不把全套设计长期装入上下文。不存在必须依赖外部 Skill 的前置步骤。

跨账号续接提供成果与必要上下文，不假设能无损迁移原生会话。用户明确要求接手后，新的指挥读取精简记录，先简报完成项、未决事项和下一步；控制版本转移后旧指挥不得继续派发。

用户离线时，需要决定的事项说明原因并保存待办，仅阻塞依赖步骤；资源不足必须确认、全部低额度必须暂停，不能用无人值守为由绕过。项目本身尚未解决的问题见[当前未决事项](../open-items.md)，已解决结论并回对应专题，不累积历史日志。

重试等待、可信实际执行、让号和只读静默核查采用[统一恢复规则](../busy-recovery.md)，不由指挥逐次唤醒或累计次数限额控制。
