# 实施路线与验收标准

[项目入口](../../README.md) · [方案总览](README.md)

更新日期：2026-11-01（北京时间）。本文为设计与调研记录，不代表功能已经实现。

## 实施原则

- 先验证风险最大的环节：官方 Server 能否在独立目录中以指定账号执行任务，额度能否归属到该账号。只有这一点成立，后续架构才有意义。
- 允许先用最小探针确认协议，再把验证过的部分固化为正式适配器；不为未经验证的协议预建完整框架。
- 能用 Fake 适配器测试的逻辑，不消耗真实额度测试。

## 实施阶段与验收门槛

### 阶段 0：确认基线

- 记录桌面程序、Server、Agent 与协议版本，明确实际启动路径。
- 对当前账号导出去重，并验证至少两个不同账号是否有效。
- 建立独立测试目录和测试仓库，不复用现有默认实例的会话或工作树。

### 阶段 1：单实例适配器原型

产出：`runtime/types.ts` 接口、`zcode-server` 适配器初版、最小 CLI（启动实例、派发任务、打印事件），以及脱敏后的协议录制样本。暂不实现 daemon 与 MCP。

验收项：

1. 不设置图形显示环境、不启动 Electron，服务进入 ready 状态。
2. 独立目录中正确加载目标账号，provider 明确为目标 Start Plan。
3. 执行一个范围很小的代码任务，核验真实文件修改及测试结果。
4. 在同一会话追加任务，验证上下文续接。
5. 记录任务前后账号额度信息、时间和用量；若额度刷新延迟或不可观测，明确标为尚未验证，不宣称通过。
6. 原始协议消息能转换为归一化事件；至少录到一次审批和一次错误响应。限流类错误若无法自然复现，标为未覆盖。
7. 若运行时提示登录或客户端依赖，记录具体缺失能力，按需验证初始化步骤，避免直接改写鉴权代码。

### 阶段 2：多 Worker 运行与恢复

产出：`accounts`、`supervisor` 和 `store` 模块，以及 daemon 骨架（先只提供 CLI 接入）。

- 两个不同账号、两个 Server 根目录、两个工作区，同时执行小任务。
- 确认账号、会话、数据库、锁和文件修改没有串用。
- 核查两边实际 provider 与额度归属，不假设多账号吞吐线性增长。
- 验证 daemon 退出后 `zcode serve` 是否继续运行，以及 daemon 重启后能否对账并接管。
- 测试连接断开、重新连接、Worker 进程重启、取消和审批等待。
- 若无法确认任务已停止或从未执行，不自动重发。

### 阶段 3：编排、MCP 与开发闭环

产出：`orchestrator`、`workspace`、`events` 模块，以及 MCP 薄入口。

- 用 Fake 适配器覆盖状态机、幂等派发、退避续跑、熔断、风控停用、对账恢复和交接流程。
- 完成事件游标、摘要与返回大小限制、按需分页读取和核验命令执行。
- 验证 `zcode_wait` 在 Codex 工具超时内返回，且能同时等待多个任务。
- 编写 Codex 侧工作流说明，跑通"任务拆解 → 并行执行 → 审查差异 → 核验 → 集成"的完整流程。
- 验证 Codex 关闭或 MCP 进程退出后，任务继续执行，重连后可以继续管理。

### 阶段 4：按需扩展

- 把 MCP 配置与 Codex 工作流说明打包为技能或插件。
- 可视化面板、更多 Worker、容器或系统用户隔离。
- ZCode 升级流程：新版本先运行协议契约测试，通过后再扩大适配器白名单。
- 若方案 A 暴露无法解决的能力缺口，再验证官方 Web 模式并以新适配器接入；只有确需完整桌面环境时才使用 Electron + Xvfb。

开始验证前先阅读[系统架构](architecture.md)与[实例运行规范](worker-runtime.md)，协议和状态设计见[任务调度](task-orchestration.md)。
